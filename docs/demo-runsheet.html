W3-D1-02React.memo with a custom comparator

BUILT PremiumBadge is memoised with a comparator that compares the formatted currency string, so a premium moving by a paisa would not re-render a badge whose text is identical.

WHY WEAK The comparator can never run. PremiumBadge is rendered only by PolicyRow, which is itself memoised on a referentially stable premium — a parent that bails out never renders its child. Measured in docs/render-counts.md. And it would lose if it did run: two formatCurrency calls to skip a render that makes one, which is the exact argument I make one file away for leaving FilterStatus un-memoised.

WHY HONEST Making it fire needs a second rateBook pass pricing the same policy — a feature the app has no reason to have. The genuinely better edit is to delete the comparator and let shallow compare on amount do the job; I left it and wrote down why, because deleting it would have quietly removed the row.

W2-D2-06Split context — state vs. dispatch

BUILT Two separate contexts over one reducer, so a component needing only dispatch does not re-render when someone else's keystroke changes state.

WHY WEAK Saves zero renders here. All five wizard steps call both hooks, so there is no dispatch-only subscriber to spare. It would still save zero if one existed — QuoteWizardPage reads state and renders the steps as its own children, so a state change re-renders them regardless of which contexts they read. Cashing the split in additionally needs React.memo on the steps.

WHY HONEST The fix is to invent a dispatch-only component the wizard does not want, and memoise steps that do not need it. That is a change made for the matrix, not for the app.

W3-D1-04useMemo on a context value

BUILT AuthProvider's value is memoised on [role, switchRole], with useCallback on switchRole beside it.

WHY WEAK The bail-out branch is unreachable in this tree. role is the provider's only state and nothing above it re-renders, so the provider re-renders exactly when role changes — which is exactly when the value must change anyway. The general hazard is real; it does not currently apply here, and the file's header used to state it as though it did.

WHY HONEST Making it observable needs a second piece of state in the provider, or a re-rendering ancestor. Both would be invented. It stays because it is correct-by-construction the moment either appears — and the useCallback next to it is load-bearing today.

C-07useFormStatus — one of two call sites is unobservable

BUILT A shared SubmitButton reading useFormStatus(), used by both the intake wizard and the Claims-tab quick form, plus WizardNavButton and FormCancelButton reading the same status.

WHY WEAK Only the wizard shows it. PolicyClaimsTab.handleLogClaim closes the modal on its first line — before the await — so the whole form unmounts before pending can render. Demo it on stop 6, never on stop 4.

WHY HONEST The fix is keeping the modal open until the action settles, which would cover the optimistic row underneath that is the actual feedback. The two features are in genuine tension and the hook loses. I recorded that rather than reordering the code to make one row look better at the expense of the UX.

W2-D1-01Mount-only fetch ([] deps)

BUILT useFetch's effect keyed on the caller's deps — [policyId] for the claims tab — which does run exactly once on the tab's first mount.

WHY WEAK That is the mount case, but it is an argument for not building the row, not a demonstration of it. No []-deps fetch exists anywhere in the app.

WHY HONEST Adding one to the claims tab ships the precise bug the hook exists to prevent: Router reuses the tab instance across :id changes, so POL-1's claims would show under every policy forever. W3-D4-04useLayoutEffect vs useEffect — not built, the only [ ] in the file

WAS BUILT StickyPremiumSummary measured the quote wizard's header in a useLayoutEffect and fed the result to the bar's top, with a lab toggle that swapped the layout effect for a passive one so the correction landed after paint instead of before it.

WHY IT WENT Two steps. The bar moved from position: fixed to sticky because product wanted it to travel with the wizard — that alone made the flicker invisible, and the row went to [~].
